# Робот-тележка: движение по точкам на полу

Учебный проект на C++20 по аппаратной схеме, программной структуре и циклограмме из этой папки. Цель — показать сущности и последовательность работы. Реальные USB, UART/CAN, компьютерное зрение, PWM и энкодеры заменены простыми моделями.

## Основные сущности

UML-диаграмма деятельности и диаграмма состояний по циклограмме находятся в [docs/robot-diagrams.md](docs/robot-diagrams.md). Исходники PlantUML, PNG и SVG сохранены в `docs/uml/`. Машина состояний реализована в `Robot`; оборудование остаётся учебной имитацией.

| Сущность | Ответственность |
| --- | --- |
| `Point`, `Pose`, `FloorPoint` | Координаты на полу, положение робота, идентифицируемая метка |
| `Route` | Порядок точек и текущая цель |
| `Camera`, `Frame` | Получение наблюдений камеры |
| `VisionSystem` | Выделение точек и преобразование координат изображения в координаты пола |
| `MotionPlanner` | Проверка достижения точки и расчёт линейной/угловой скорости |
| `DriveController`, `Telemetry` | Команды контроллеру и обратная связь: одометрия, препятствие, аварийная кнопка, watchdog |
| `Robot` | Запуск, остановка и последовательное выполнение маршрута |
| `TaskScheduler` | Периодические вызовы навигации и контроллера в отдельных потоках |

## Логика

```text
Initializing → подключение камеры и контроллера
  → WaitingForReady → подтверждение готовности → Ready
  → оператор загружает маршрут и нажимает Пуск → Moving
  → проверка телеметрии и датчиков
  → кадр камеры → распознавание точек → координаты пола
  → поиск текущей точки маршрута
  → сравнение с положением из одометрии
  → расчёт команды скорости → контроллер → приводы
  → новый кадр и коррекция движения
  → точка достигнута → следующая точка
  → последняя точка достигнута → команда Стоп → Stopping
  → контроллер подтвердил нулевую скорость → Completed
```

При потере целевой метки робот останавливается и ждёт следующего кадра, сохраняя `Moving` и текущую цель. `stop()` оператора переводит его в `Stopping`, а подтверждение остановки — в `Stopped`. Причина хранится в `StopReason`.

Подключение, готовность и подтверждение остановки имеют тайм-аут по 2 секунды. Ошибки оборудования, потеря связи, аварийные входы и тайм-ауты переводят робот в `Fault`. Его причина доступна в `status().faultReason`. Проверка аварий выполняется во всех рабочих состояниях.

`loadRoute(Route)` принимается в `Ready`, `Completed` и `Stopped` при готовом оборудовании и непустом маршруте. Затем отдельный `start()` запускает движение. `resetFault()` разрешён только после устранения аварийных условий и подтверждения остановки; он возвращает робот в `Initializing`, очищая прежний маршрут. Автоматического продолжения после ошибки нет.

Навигация вызывается раз в 100 мс, модель контроллера — раз в 20 мс. Общие данные робота и контроллера защищены своими мьютексами. При завершении сначала останавливаются и присоединяются рабочие потоки, затем останавливается и уничтожается робот.

## Файлы

- `CMakeLists.txt` — описание проекта, библиотека `robot_core`, программа `robot_demo`, проверки `robot_tests`.
- `include/robot/types.hpp` — данные предметной области.
- Каждый класс имеет заголовок `include/robot/<имя>.hpp` с объявлениями и реализацию `src/<имя>.cpp`.
- `camera.hpp` / `camera.cpp` — интерфейс камеры.
- `drive_controller.hpp` / `drive_controller.cpp` — интерфейс контроллера приводов.
- `route.hpp` / `route.cpp` — порядок точек и продвижение по маршруту.
- `vision_system.hpp` / `vision_system.cpp` — распознавание и координаты меток.
- `motion_planner.hpp` / `motion_planner.cpp` — расчёт движения к цели.
- `robot.hpp` / `robot.cpp` — основной цикл управления.
- `task_scheduler.hpp` / `task_scheduler.cpp` — планировщик периодических задач.
- `simulated_camera.hpp` / `simulated_camera.cpp` — имитация камеры.
- `simulated_drive_controller.hpp` / `simulated_drive_controller.cpp` — имитация контроллера.
- `src/main.cpp` — сборка объектов и сценарий оператора.
- `tests/robot_tests.cpp` — проверки маршрута, остановки и аварийных условий.

Предыдущие примеры в `task-planner/` и `thread-task-manager/` не входят в сборку робота.

## Сборка и запуск

```sh
cmake -S . -B build
cmake --build build
ctest --test-dir build --output-on-failure
./build/robot_demo
```

Нужны CMake 3.20+ и компилятор со стандартной библиотекой C++20, поддерживающей `std::jthread`. Сторонних библиотек нет. Демонстрация проходит три точки; предусмотрен лимит времени 15 секунд.

## Подключение к Raspberry Pi с Mac

В терминале из папки проекта запустите:

```sh
python3 scripts/connect_raspberry.py
```

Скрипт до 120 секунд ждёт, пока маршрут к `1.1.1.1` перестанет проходить через
VPN-интерфейс. VPN нужно отключить вручную; проверка маршрута не определяет все
варианты VPN со split tunneling. Затем скрипт проверяет `bkzs.local:22`.
Если устройство по этому имени недоступно, он ищет открытый порт 22 в текущей
IPv4-подсети и предлагает выбрать адрес Raspberry Pi. Один открытый SSH-порт
не подтверждает модель устройства. После выбора скрипт спрашивает логин и
открывает обычную SSH-сессию; пароль или подтверждение ключа сервера запросит SSH.

Логин и известный адрес можно передать сразу:

```sh
python3 scripts/connect_raspberry.py --user pi
python3 scripts/connect_raspberry.py --user YOUR_LOGIN --host 192.168.1.50
```

Используйте логин, заданный при настройке Raspberry Pi. Параметр `--wait 300`
увеличивает ожидание отключения VPN до пяти минут, а `--subnet 192.168.1.0/24`
задаёт подсеть для поиска. Нужны macOS, Python 3 и включённый SSH на Raspberry Pi.
Сторонние Python-пакеты и `nmap` не требуются.

Для проверки порта 22 на каждом адресе локальной сети есть отдельный скрипт:

```sh
python3 scripts/scan_ssh.py
python3 scripts/scan_ssh.py --user YOUR_LOGIN
```

Первый запуск показывает результат TCP-соединения и SSH-баннер для каждого
адреса, кроме самого Mac. Второй дополнительно пробует вход с указанным логином
на каждое устройство с открытым портом 22, используя стандартные SSH-ключи и
ssh-agent. Можно задать ключ через `--identity ~/.ssh/id_ed25519`.
При успешном входе выполняется команда `true`, после чего сессия закрывается.
Пароли не запрашиваются. Пользовательский SSH-конфиг не используется; файл
`known_hosts` проверяется через временную копию и не изменяется. Новые ключи
серверов принимаются в этой временной копии на время запуска.
Имя устройства `bkzs` не считается логином.

Параметры `--subnet` и `--wait` работают как у скрипта подключения;
`--timeout 2` увеличивает тайм-аут проверки порта до двух секунд.
Открытый порт 22 сам по себе не подтверждает, что устройство — Raspberry Pi.

## Где модель упрощена

`Frame` содержит кандидаты в метки вместо сырых пикселей. `SimulatedCamera` возвращает фиксированную сцену. В `VisionSystem` калибровка заменена масштабом 1000 пикселей на метр; предполагается единая система координат пола и одометрии. Для камеры на движущемся роботе нужна полноценная калибровка и преобразование координат с учётом его положения.

`SimulatedDriveController` интегрирует командную скорость вместо физических энкодеров и не моделирует проскальзывание. `stoppedConfirmed` устанавливается только при обновлении модели приводов, когда фактическая скорость равна нулю. Отправка новой команды сбрасывает прежнее подтверждение. Watchdog блокирует движение через 500 мс без новых команд движения и снимается явным сбросом ошибки; при ожидании в покое он не срабатывает. Аварийные входы показаны в телеметрии и проверены подстановкой данных в тестах; реальные GPIO здесь не реализованы. В настоящем роботе контроллер приводов работает на отдельном микроконтроллере, а не в потоке Raspberry Pi.

Планировщик не обеспечивает жёсткое реальное время. Долгие задачи пропускают желаемый период; остановка ждёт завершения текущего вызова. Исключение рабочего потока передаётся в основной поток через `rethrowIfFailed()`. Уничтожать планировщик нужно из владеющего потока. Оборудование должно жить дольше объекта `Robot`. Методы адаптеров должны возвращаться быстро: подключение и готовность запрашиваются отдельно от опроса результата; блокирующий вызов нельзя прервать тайм-аутом машины состояний.
